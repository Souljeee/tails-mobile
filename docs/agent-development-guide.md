# Руководство по агентской разработке

Этот документ дополняет корневой `AGENTS.md`. Он описывает целевое устройство Flutter-кода в
`tails_mobile` и служит основой для реализации и ревью изменений.

## 1. Главный принцип

Предпочитай самое простое решение, которое:

- соответствует существующей архитектуре;
- явно разделяет UI, состояние, бизнес-сценарий и ввод-вывод;
- тестируется без запуска всего приложения;
- не увеличивает публичную поверхность без необходимости;
- не делает несвязанного рефакторинга.

Сначала ищи аналогичную feature и повторяй её соглашения. Если существующий код расходится с этим
руководством, не переписывай его попутно: новый и существенно изменяемый код веди к целевым
правилам, а миграцию делай отдельной задачей.

## 2. Архитектура и границы

Проект использует feature-first структуру с локальным разделением по ответственности:

```text
lib/src/
  core/                         # Общие технические механизмы и UI kit
  feature/<feature>/
    presentation/               # Экраны, виджеты, presentation models/UIO
    domain/                     # Bloc, event, state, бизнес-сценарии
    data/
      repositories/             # Оркестрация источников и преобразование моделей
      data_sources/             # HTTP, storage, database, platform API
      data_sources/dtos/        # Формат внешних данных
```

Для большой feature допустим `<feature>/core` для сущностей, действительно общих только её
подфичам. Не переноси код в глобальный `core` ради потенциального переиспользования: сначала должно
появиться реальное использование в нескольких features.

### Направление зависимостей

- Presentation знает о Bloc, его state/event и presentation/domain моделях.
- Bloc знает о repository, но не о виджетах, `BuildContext`, Navigator и data source.
- Repository скрывает выбор источника данных, кэширование и преобразование DTO <-> model.
- Data source работает с внешней системой и возвращает DTO/технический результат.
- DTO не должен просачиваться в presentation.
- Одна feature не импортирует внутренности другой feature. Общий контракт подними в подходящий
  общий уровень или предоставь узкий публичный фасад.

Зависимости приложения создаются в composition root и передаются через существующий
`DependenciesContainer`/`DependenciesScope`. Не создавай repository, HTTP-клиент или storage внутри
виджета либо Bloc.

### Модели и ошибки

- DTO отражает внешний контракт; domain/presentation model отражает потребности приложения.
- Преобразование держи у границы repository/data, а не в виджете.
- Используй типы вместо `Map<String, dynamic>` за пределами слоя сериализации.
- Не проглатывай исключения. Bloc может вызвать `addError(error, stackTrace)` и перевести состояние
  в понятную ошибку; repository должен преобразовывать только те ошибки, семантику которых знает.
- Не показывай пользователю текст сырого исключения или серверный stack trace.

## 3. State management с BLoC

В проекте один основной подход — `Bloc<Event, State>`. Не смешивай его с локаторами сервисов,
Provider/Riverpod/MobX и глобальными mutable singleton без отдельного архитектурного решения.

### Events

- Называй событие по намерению пользователя или факту системы: `fetchRequested`, `retryRequested`,
  `dateSelected`, а не `callApi` или `setLoading`.
- Делай sealed event-классы неизменяемыми и сравнимыми через `Equatable`, следуя существующему
  factory + `map` стилю feature.
- Передавай минимально необходимые данные. Не передавай `BuildContext`, Widget, controller или
  callback в event.

### States

- Состояние — неизменяемый снимок UI, а не набор команд для интерфейса.
- Моделируй существенные варианты явно: loading/success/error либо единое состояние с независимыми
  статусами, если на экране несколько параллельных операций.
- Все поля, влияющие на UI, включай в `Equatable.props`.
- Не используй `null` сразу для нескольких смыслов. Для nullable-обновлений следуй принятому в
  проекте `CopyWithWrapper` или явным вариантам состояния.
- Одноразовые эффекты (навигация, snackbar, закрытие modal) обрабатывай в `BlocListener`, а не во
  время построения UI. Не помещай `BuildContext` в Bloc.

### Bloc и асинхронность

- Обработчик события координирует сценарий; сетевые и storage-детали остаются в repository/data
  source.
- Выбирай transformer осознанно: `restartable` для поиска/перезапрашиваемых фильтров, `droppable`
  для защиты повторной отправки, `sequential` для операций, где важен порядок. Не добавляй его без
  реальной проблемы конкурентности.
- После `await` учитывай закрытие Bloc и актуальность результата. Не создавай fire-and-forget Future
  без `unawaited` и явного понимания жизненного цикла.
- Ресурсы, созданные Bloc/виджетом, должны закрываться владельцем (`close`, `dispose`, cancel).

### Граница с UI

- Используй `BlocBuilder` только вокруг поддерева, которое зависит от состояния.
- Применяй `buildWhen`/`BlocSelector`, когда это заметно уменьшает лишние перестроения, но не ради
  формальной оптимизации.
- Callback виджета отправляет event; он не дублирует бизнес-правила из Bloc.
- Простое эфемерное UI-состояние (фокус, анимация, выбранная вкладка внутри локального контрола)
  может жить в `StatefulWidget`. Состояние бизнес-сценария должно жить в Bloc.

## 4. UI и композиция виджетов

### UI kit обязателен

Перед реализацией интерфейса проверь `lib/src/core/ui_kit`:

- кнопки — `UiButton` и существующие варианты;
- поля — `UiTextField` и его controller/validators;
- app bars, checkbox, radio, popup, loader, shimmer и ошибки — существующие `Ui*` компоненты;
- цвета и типографика — extensions темы (`context.uiColors`, `context.uiFonts`);
- assets — сгенерированный `UiAssets`/предоставленные theme extensions.

`Scaffold`, layout-примитивы, slivers и другие структурные Flutter-виджеты можно использовать
напрямую. Но не создавай локальную копию кнопки, поля, app bar или visual token через сырой
Material-виджет/магическое значение, если аналог уже есть в UI kit.

Если нужного компонента нет:

1. Определи, специфичен ли он для feature. Специфичный виджет оставь внутри feature.
2. Если компонент повторяемый и не знает о feature-моделях, добавь его в UI kit.
3. Сделай API небольшим, типизированным и согласованным с соседними `Ui*` компонентами.
4. Покрой существенные состояния: default, disabled, loading, error/selected — где применимо.

### Виджеты вместо build-методов

Не делай так:

```dart
Widget _buildHeader(BuildContext context) => ...;
Widget _buildPetCard(PetModel pet) => ...;
```

Делай так:

```dart
final class _Header extends StatelessWidget {
  const _Header({required this.title});

  final String title;

  @override
  Widget build(BuildContext context) => ...;
}
```

Отдельный виджет создаёт явную границу перестроения, получает типизированные параметры и проще
тестируется. Оставляй в `build` только короткую композицию. Маленькие callbacks допустимы; функции,
возвращающие отдельные UI-секции, — нет. Повторяемые list item, loading/error/empty состояния и
крупные секции всегда оформляй виджетами.

### Дополнительные UI-правила

- Предпочитай `const` constructors и финальные поля.
- Не храни вычисляемое представление данных в нескольких местах; подготовь его в model/UIO или
  чистой функции и протестируй.
- Не выполняй I/O, навигацию или dispatch события из `build`.
- После асинхронного разрыва проверяй `context.mounted` перед использованием `BuildContext`.
- Учитывай SafeArea, клавиатуру, text scale, длинные переводы и малые экраны.
- Пользовательский текст добавляй в ARB и получай через `context.l10n`.
- Для новых изображений и иконок обновляй assets и используй сгенерированный доступ, а не строковый
  путь.
- Не оптимизируй производительность догадками; избегай очевидно тяжёлой работы в `build` и измеряй
  сложные случаи.

## 5. Навигация

Основная навигация построена на типизированном `go_router` и описана в
`lib/src/core/navigation/routes.dart`.

- Для нового экрана добавь `TypedGoRoute`/ветку и тип `GoRouteData`.
- Переход выполняй через сгенерированный route-объект (`go`, `push`, `replace` по нужной семантике),
  а не через строку пути.
- Обязательные route-параметры делай типизированными constructor-параметрами. Не передавай большой
  mutable object через глобальное состояние только ради навигации.
- Авторизационные и другие глобальные redirects держи в guards/router, а не размазывай по экранам.
- Сохраняй независимую историю tab-веток через существующий `StatefulShellRoute`.
- `Navigator.pop` допустим для закрытия dialog/bottom sheet и возврата локального результата.
- Для нового полноценного экрана не используй `Navigator.push(MaterialPageRoute(...))`.
- Решай, кому принадлежит Bloc, до перехода: владелец создаёт и закрывает его; route не должен
  случайно создавать дублирующий глобальный Bloc.

После изменения типизированных маршрутов обязательно запусти code generation и не редактируй
`routes.g.dart` вручную.

## 6. Data layer

- Data source отвечает за один технический источник: REST, database, secure storage или platform
  API.
- Repository предоставляет feature-ориентированный API и скрывает DTO/транспорт.
- Не допускай HTTP status codes, JSON keys и storage keys в Bloc или presentation.
- Side effects repository (например, поток обновлений) должны иметь явного владельца и корректное
  завершение. Не создавай бесконтрольно broadcast streams.
- Для дат, enum и nullable-полей определяй однозначный формат на границе сериализации.
- Не логируй токены, персональные данные и содержимое secure storage.

## 7. Тестирование

Тестируй поведение на самом низком разумном уровне:

- чистые преобразования и модели — unit tests;
- Bloc — последовательности event -> state, ошибки и конкурентные сценарии;
- repository — взаимодействие с data source и преобразование DTO/model;
- важные UI-состояния и пользовательские действия — widget tests;
- маршруты/guards — redirect и корректность параметров.

Каждый bug fix должен по возможности начинаться с теста, воспроизводящего дефект. Тесты не должны
зависеть от реальной сети, текущего времени или случайности: используй mock/fake и доступный `clock`.
Проверяй не детали реализации, а наблюдаемое поведение.

## 8. Code style и generated code

- Следуй `analysis_options.yaml`, Dart 3 и ширине строки 100.
- Используй package imports для `lib/`.
- Публичные и локальные типы должны быть явно типизированы; избегай `dynamic`.
- Имена файлов — `snake_case`, типов — `UpperCamelCase`, членов — `lowerCamelCase`.
- Не редактируй generated-файлы. Источник истины — аннотированный Dart/ARB/schema файл.
- Не добавляй lint ignore на уровне файла. Точечный ignore допустим только с комментарием, почему
  безопасное исправление невозможно.
- Комментарий объясняет причину или ограничение, а не пересказывает код.

## 9. Рабочий процесс агента

### Исследование

1. Найди точку входа и похожую реализацию через `rg`.
2. Прочитай весь затрагиваемый поток: UI -> Bloc -> repository -> data source -> тесты.
3. Зафиксируй текущие локальные изменения и не присваивай их себе.
4. Если требования неоднозначны, выбери обратимое минимальное решение; спроси пользователя только
   когда варианты существенно меняют продукт или публичный контракт.

### Реализация

- Делай небольшие логически связанные изменения.
- Сохраняй обратную совместимость, если задача явно не требует breaking change.
- При изменении контракта обновляй всех потребителей и тесты в том же изменении.
- Не форматируй и не переписывай несвязанные файлы.
- Не удаляй код и данные «для чистоты», если это не входит в задачу.
- Новые зависимости добавляй только после проверки, что SDK и текущий стек не решают задачу.

### Самопроверка

Перед завершением ответь «да» на вопросы:

- Слои и направление зависимостей сохранены?
- UI использует UI kit и состоит из виджетов, а не `_build*` методов?
- Бизнес-состояние находится в Bloc, а одноразовые эффекты — в listener/UI?
- Экран добавлен в typed router без строкового пути/`MaterialPageRoute`?
- Нет ручных изменений generated-кода?
- Есть тесты для нового или исправленного поведения?
- Форматирование, analyzer и релевантные тесты прошли?
- Diff содержит только изменения текущей задачи?

## 10. Команды проекта

Проект закреплён на Flutter из `.fvmrc`, поэтому локально предпочитай FVM:

```sh
fvm flutter pub get
fvm dart run build_runner build -d
fvm dart format --line-length 100 lib test
fvm flutter analyze
fvm flutter test
```

Для пакетов workspace запускай релевантные проверки также из `packages/app_database` или
`packages/rest_client`, если они были изменены. Не запускай codegen без причины после изменений,
которые не затрагивают его источники.
